# Section 1: Project Overview & Technology Stack

## 1.1 System Description

The **Digital Grade-Report Locker (DGRL)** is a secure, mobile-first academic result management system built for university environments. The system serves two distinct categories of users: **system administrators**, who manage student records, courses, and grades through a dedicated control panel, and **students**, who access their academic performance data — including semester grades, GPA, CGPA, and full academic history — through a personalized dashboard.

The core problem DGRL solves is the transition from paper-based or fragmented digital grade management to a centralized, real-time, mobile-accessible platform. Instead of relying on printed result slips or department notice boards, students can log in from their mobile devices to view their complete academic transcript, broken down by semester with computed grade-point averages. Administrators gain the ability to perform bulk operations — including Excel-based imports — that drastically reduce the manual data-entry overhead traditionally associated with grade management.

## 1.2 Architecture Layout

The application follows a **layered architecture** with four distinct tiers that communicate sequentially:

**Presentation Layer (UI / Screens)** — This is the topmost layer consisting of Flutter `StatefulWidget` and `StatelessWidget` classes organized across 16 screen files under `lib/screens/`. Each screen is responsible for rendering its portion of the user interface and delegating data requests to the state-management layer. Screens never directly call Firebase or perform I/O operations; they only invoke methods on providers or services.

**State Management Layer (Providers)** — The `provider` package (version 6.1.2) serves as the global state hub. Two provider classes reside in `lib/providers/`: `AppProvider`, which manages authentication status, student profile data, grades, courses, GPA calculations, notifications, and real-time data synchronization; and `ThemeProvider`, which manages light/dark theme preferences. These providers extend `ChangeNotifier` and call `notifyListeners()` after any state mutation, which triggers a rebuild of all `Consumer` widgets that depend on that data. This pattern avoids prop drilling — deeply nested widgets do not need to receive callbacks or data through constructors; they simply read from the nearest `Provider<AppProvider>` ancestor in the widget tree.

**Service Layer (Business Logic / Data Access)** — Nineteen service classes in `lib/services/` encapsulate all Firebase interactions, file I/O, and business rules. Services such as `AuthService` handle login/logout and credential caching; `GradeService` computes GPA and CGPA using credit-hour weighting; `ExcelImportService` parses `.xlsx`/`.xls`/`.csv` files and yields staging rows for preview before committing to the database. Services are instantiated by the providers and are never directly accessed from the UI layer.

**Data Layer (Firebase Backend)** — The persistent data store is Firebase, comprising three primary services: `firebase_core` for initialization, `cloud_firestore` (Firestore) as the document-oriented NoSQL database, and `firebase_auth` for authentication. Firestore is organized into three root collections: `students` (keyed by `student_id`), `courses` (auto-generated document IDs), and `grades` (auto-generated document IDs). `firebase_storage` provides image upload capability for student profile photos. The `firebase.json` configuration and `lib/firebase_options.dart` (generated by the FlutterFire CLI) wire the project to the correct Firebase project instance.

## 2.2 Models Layer (`lib/models/`)

The models directory contains four Dart classes that serve as the **canonical data contract** between the Firestore document structure and the application's Dart objects. Each model implements two factory methods — `fromMap(Map<String, dynamic>)` for deserializing Firestore documents into Dart objects, and `toMap()` for serializing Dart objects back into the map format that Firestore expects. This bidirectional mapping is essential because Firestore operates on map-based documents rather than typed objects.

**`student.dart`** — Defines the `Student` class with fields: `studentId`, `fullName`, `department`, `batch`, `email`, `password`, `sex`, `phone`, `age`, `photoUrl`, and `uid`. The `uid` field stores the Firebase Authentication user ID, linking the Firestore student record to the Auth system. Key methods include `toUpdateMap()` which uses `FieldValue.serverTimestamp()` for tracking updates, and `toPublicMap()` which omits the password and uid fields for safe sharing. `copyWith()` enables immutable update patterns — the `AppProvider.updateStudentProfile()` method creates a new `Student` instance with only the changed fields rather than mutating the existing object.

**`grade.dart`** — The `Grade` class is the most logic-dense model. It stores `studentId`, `courseCode`, three score components (`midScore`, `assignmentScore`, `finalScore`), the computed `totalScore`, a `letterGrade` string, and the `semester` identifier. The static method `calculateLetterGrade(double total)` implements a 10-level grading scale (A+ through F) with 5-point granularity in the B/C range. The static method `gradePoint(String letter)` maps each letter grade to its numeric quality point value on a 4.0 scale (A+ and A = 4.0, A- = 3.75, B+ = 3.5, B = 3.0, B- = 2.75, C+ = 2.5, C = 2.0, C- = 1.75, D = 1.0, F = 0.0). The `Grade.create()` factory constructor automatically computes `totalScore = midScore + assignmentScore + finalScore` and derives the `letterGrade` from the total, ensuring that every grade record is internally consistent when first created.

**`course.dart`** — Contains two classes: `Course` and `CourseSchedule`. The `Course` class holds `courseCode`, `courseTitle`, `creditHours`, `instructor`, `semester`, `department`, capacity tracking (`maxCapacity`, `currentEnrolled`), prerequisites, schedule, and room assignment. The `isFull` / `hasAvailability` computed booleans enable the admin panel to display enrollment status at a glance. `CourseSchedule` encapsulates day-of-week, start/end time, and schedule type (lecture/lab/tutorial), providing `formattedTime` and `formattedSchedule` getters for display.

**`course_registration.dart`** — The `CourseRegistration` class models the many-to-many relationship between students and courses. Each registration record captures `studentId`, `courseCode`, `semester`, `registrationDate`, and a `status` field that can be 'registered', 'dropped', 'completed', or 'failed'. The `CourseRegistration.create()` factory generates a composite document ID (`studentId_courseCode_semester`) for idempotent registration.

## 2.3 Providers Layer (`lib/providers/`)

**`app_provider.dart`** — This file (376 lines) is the central nervous system of the application. It extends `ChangeNotifier` and owns the following state:

- **Authentication State:** `_currentStudent` (Student object or null), `_isLoggedIn` (boolean), exposed via getters. The `login()` method accepts an ID and password, delegates to `AuthService.login()` which auto-detects admin vs. student credentials, then populates the student profile and triggers `loadStudentData()` on success. The `logout()` method resets all state fields to defaults and calls `notifyListeners()`, which causes every listening widget to rebuild with empty data.

- **Academic Data State:** `_grades` (list of Grade objects fetched from Firestore), `_courses` (list of Course objects), `_semesters` (list of semester strings extracted from grades), `_gpa` (current semester GPA), `_cgpa` (cumulative GPA across all semesters), `_selectedSemester` (the most recently active semester), `_selectedGPA` (GPA for the selected semester). The `loadStudentData()` method orchestrates four parallel fetch operations: grades for the student, semester list, CGPA computation, and course catalog, then sets the selected semester to the latest one.

- **Notification State:** `_notifications` and `_unreadNotificationCount` manage the in-app notification inbox. Notifications are generated when grades are added, data is updated, or admin sends a broadcast.

- **Real-Time Listeners:** The `initializeRealtimeListeners()` method attaches three Firestore snapshot listeners on initialization: one listening to the student's document for profile changes, one listening to the grades collection for new or updated grades, and one listening to the courses collection for catalog changes. Each listener callback updates the corresponding state field and calls `notifyListeners()`, enabling live UI updates without manual refresh.

- **Profile Update:** The `updateStudentProfile()` method constructs an update map, calls `RealtimeService.updateStudentWithSync()` which writes to Firestore, and then updates the local `_currentStudent` object via `copyWith()`.

**`theme_provider.dart`** — Manages light/dark theme mode with SharedPreferences persistence. The `loadTheme()` method reads the stored preference on app start, while `toggleTheme()` flips the value, persists it, and calls `notifyListeners()`. The `lightTheme` and `darkTheme` getters return configured `ThemeData` objects with Material 3 enabled and an indigo color scheme.

## 2.4 Constants & Theming (`lib/constants/theme_constants.dart`)

This file (188 lines) provides a centralized design system that every screen imports. It is divided into three classes:

**`AppColors`** — A palette of 20+ named color constants. Primary colors (`primary`, `primaryLight`, `primaryDark`) define the indigo-based brand identity. Semantic colors (`success`, `warning`, `error`, `info`) are used consistently across forms, dialogs, and status indicators. Grade-specific colors (`gradeA` green, `gradeB` blue, `gradeC` amber, `gradeD` orange, `gradeF` red) are used in the `AppTextStyles.gradeColor()` and `AppTextStyles.gradeBgColor()` methods to color-code grade badges.

**`AppTheme`** — Provides reusable `BoxDecoration` objects that define common card styles: `gradientCard` (a linear gradient from primary to secondary with a drop shadow), `whiteCard` (white background with subtle shadow — the most frequently used card style in the app), `glassCard` (translucent with blur for overlay effects), and `outlinedCard` (white with a border for compact tiles). These are used directly in screen builds rather than repeating decoration parameters.

**`AppTextStyles`** — A set of 8 named text styles (`h1` through `caption`, plus `button`) that enforce consistent typography. The `gradeColor(String letter)` method returns a `TextStyle` with the appropriate color for a given letter grade, enabling the grade display to be green for A-range, blue for B-range, amber for C-range, and orange for D/F.

## 2.5 Services Layer (`lib/services/`)

**`auth_service.dart`** — Handles all authentication concerns. The `login()` method implements a three-step strategy: first, it attempts an offline cache match via `_tryCachedLogin()` which checks SharedPreferences for saved credentials; second, it checks for the hardcoded admin credentials (`ADMIN` / `ADMIN123`); third, it queries Firestore's `students` collection by `student_id` or `email` and verifies the stored password. On success, it creates or reuses a Firebase Auth account, updates the student document with the `uid`, and optionally persists the session to SharedPreferences if the `remember` flag is true. The `isLoggedIn()` method returns `true` if SharedPreferences contains a saved session — this is the sole check used by the splash screen to determine whether to auto-navigate or show the login form.

**`firestore_service.dart`** — Provides CRUD operations specifically for the `students` collection. `addStudent()` creates both a Firebase Auth account and a Firestore document in a single transactional operation. `getAllStudents()` retrieves the entire collection for the admin panel's student list. `searchStudents()` and `getStudentsByDepartment()`/`getStudentsByBatch()` provide filtered queries for the admin search features. The file also includes streaming variants (`streamAllStudents()`, `streamStudentsByDepartment()`) that return `Stream<List<Student>>` for real-time admin views.

**`grade_service.dart`** — The heaviest service at 480 lines. It provides: grade retrieval (`getGradesForStudent()`, `getGradesForSemester()`), grade creation with automatic notification (`addGrade()`, `addGradeWithScores()`), GPA and CGPA calculation using credit-hour weighting (`calculateGPA()`, `calculateCGPA()`), semester extraction (`getSemesters()`), course retrieval (`getAllCourses()`, `getCourse()`), and advanced analytics (`getGradeStatistics()`, `getTopGrades()`, `getGradeCountByLetter()`). The GPA calculation iterates over each grade, looks up the course's credit hours, multiplies the grade-point value by the credits, sums the products, and divides by the total credits — the standard academic GPA formula.

**`excel_import_service.dart`** — Implements the two-phase bulk import pattern. During the **Parse** phase, `parseStudents()`, `parseCourses()`, and `parseGrades()` synchronously read an Excel file from disk, iterate over worksheet rows (skipping empty rows and validating required fields), and return a `ParseResult<T>` containing a list of mutable staging row objects (`StagedStudentRow`, `StagedCourseRow`, `StagedGradeRow`) plus any parse warnings. No database writes occur during this phase. During the **Submit** phase (triggered by the admin clicking "Submit" in the preview dialog), `submitStudents()` and `submitCourses()` and `submitGrades()` create Firebase Auth users, write documents to Firestore, and perform cross-reference validation — for grades, it checks that the student and course exist in the database and that no duplicate grade record already exists for that student/course/semester combination.

## 2.6 Root Configuration Files

**`main.dart`** — The application entry point. It initializes Firebase via `Firebase.initializeApp()` with platform-specific options from `firebase_options.dart`, optionally connects to Firebase emulators for local development when the `USE_FIREBASE_EMULATOR` environment variable is true, and then calls `runApp(const DGRLApp())`. The `DGRLApp` widget is a `MultiProvider` that registers `ThemeProvider` and `AppProvider` at the root level, making them accessible to every descendant widget via `Provider.of<T>()` or `Consumer<T>`. The app uses `Consumer<ThemeProvider>` to dynamically switch between light and dark themes.

**`pubspec.yaml`** — Declares 16 production dependencies including Firebase packages, the `provider` state management library, `file_picker` and `excel` for bulk import, `image_picker` for camera/gallery access, `pdf` and `printing` for transcript generation, `fl_chart` for GPA visualization, and `shared_preferences` for local session caching. The SDK constraint `^3.11.0` requires Dart 3.11 or later and enables pattern matching, sealed classes, and enhanced switch expressions used throughout the codebase.

**`analysis_options.yaml`** — Configures Flutter lint rules using the `flutter_lints` package. The project follows strict linting conventions that enforce type safety, null safety, and consistent code style.

# Section 3: Step-by-Step UI Flow & Run Pages Logic

## 3.1 The Authentication Flow

### Step 1: Splash Screen Initialization

When the app launches, `DGRLApp` is rendered, which displays `const SplashScreen()` as the home widget. The splash screen immediately triggers `_initializeApp()` in a post-frame callback. This method calls `provider.initialize()` on `AppProvider`, which performs two critical operations:

First, it checks `AuthService.isLoggedIn()`, which reads SharedPreferences for a key called `logged_in_student`. If this key exists — meaning the user previously logged in with "Remember Me" checked — the method returns `true` and the provider proceeds to load the saved session. If the key does not exist, `isLoggedIn` is set to `false` and the splash screen will navigate to the login form after a 3-second delay.

Second, if a saved session exists, `getCurrentUser()` reads the JSON data from SharedPreferences (which contains the student's profile fields, their role, and their password), reconstructs a `Student` object via `Student.fromMap()`, and calls `loadStudentData()` to fetch grades, courses, and GPA from Firestore. The 3-second splash delay ensures the animation completes before the navigation occurs.

After the delay and initialization, the splash screen makes a routing decision: if `isLoggedIn` is true and `currentStudent` is not null, it navigates to `EnhancedStudentDashboard` (the student homepage). If `isLoggedIn` is true but `currentStudent` is null, it navigates to `AdminPanelScreen` (indicating an admin session). If `isLoggedIn` is false, it navigates to `LoginScreen`.

### Step 2: Login Screen — Student Authentication

The `LoginScreen` presents a form with two fields: University ID and Password. The ID field accepts either the student's auto-generated ID (e.g., `bdu12345`) or their email address (`bdu12345@bdu.edu.et`). The password is the student's auto-generated password (typically the same as their student ID unless changed).

When the user taps "Login", `_handleSignIn()` is called. This method first validates the form, then calls `provider.login(id, password, remember: _rememberMe)` on `AppProvider`. The `remember` parameter controls whether the session is persisted to SharedPreferences — if true, the credentials are cached so that the student does not need to log in again on subsequent app launches.

Inside `AuthService.login()`, the authentication logic follows a three-tier strategy:

1. **Offline cache check:** The method calls `_tryCachedLogin(id, password)`, which reads SharedPreferences and checks whether the provided ID and password match the cached credentials. If they do, it returns the cached role immediately without any network call. This enables offline login for previously authenticated users.

2. **Admin detection:** If the ID is `ADMIN` and the password is `ADMIN123`, the method creates a Firebase Auth account for `admin@grade.com` (if one does not already exist), signs in, and returns the role `'admin'`. Admin credentials are hardcoded for simplicity and are intended to be changed in production.

3. **Student lookup:** For student authentication, the method queries Firestore's `students` collection by `student_id` (and by `email` if the input contains an `@` symbol). It retrieves the student document, verifies the stored password, ensures a Firebase Auth account exists (creating one if necessary), signs in, and updates the student's `uid` in Firestore. On success, it returns `'student'`.

After a successful login, `AppProvider` stores the student data, calls `loadStudentData()`, activates real-time listeners, and returns the role string to the login screen. The login screen then navigates to `MainScreen` (for students) or `AdminPanelScreen` (for admins). If authentication fails at any point, the user sees the message "Invalid ID/Email or Password" — the system deliberately avoids revealing whether the ID or password was incorrect.

### Step 3: The "Remember Me" Checkbox

The login screen includes a `Checkbox` widget bound to a `_rememberMe` boolean state variable. When the checkbox is tapped, `onChanged` fires `setState(() => _rememberMe = v ?? false)`, which immediately updates the checkbox's visual state. The `_rememberMe` value is then passed to the `login()` call. If `true`, `AuthService` saves the full student data map as a JSON string in SharedPreferences under the key `logged_in_student`. On the next app launch, `isLoggedIn()` detects this key and the user is automatically signed in, bypassing the login form entirely. If `false`, any previously saved session is deleted on each login via `prefs.remove(_loggedInKey)`.

## 3.2 The Admin Operations Panel

### Screen Layout

`AdminPanelScreen` is a StatefulWidget with five tabs: Dashboard, Students, Courses, Grades, and More (for settings and import). All tabs share a consistent layout pattern: a header row with a title and action buttons (Import and Add), followed by an `Expanded` list.

### Manual Student Creation

When the admin taps "Add" on the Students tab, `_showAddStudentDialog()` presents a form with fields for Student ID, Full Name, Department, Batch, Phone, Age, and Sex. The Student ID field has an `onChanged` listener that calls `_autoFill()` — this method normalizes the ID by prepending the `bdu` prefix if missing, then automatically populates the (read-only) email field as `bduXXX@bdu.edu.et` and the password field with the normalized ID. This ensures that every student created through the admin panel has a predictable email and password format.

On save, the method validates that the ID and name are non-empty, constructs a `Student` object, and calls `FirestoreService.addStudent()`. This service method first creates a Firebase Auth account using `auth.createUserWithEmailAndPassword()`, then writes the student document to the Firestore `students` collection with the student ID as the document key.

### Bulk Excel Import — Two-Phase Staging Pattern

The bulk import feature is available from four locations: the Dashboard's "Import from Excel" Quick Action, the More tab's "Import from Excel", and the Import buttons on the Students, Courses, and Grades tabs. Tapping any of these triggers the following flow:

**Phase 1 — File Picking and Parsing:** The admin selects a file type (students, courses, or grades — with tab-specific buttons skipping this prompt). `ExcelImportService.pickExcelFile()` opens the native file picker filtered to `.xlsx`, `.xls`, and `.csv` extensions. After file selection, the corresponding `parse*` method reads the file bytes, decodes the Excel workbook, iterates over rows starting from index 1 (skipping the header row), extracts cell values, normalizes student IDs, and validates required fields. Empty rows are silently skipped. The result is a `ParseResult<T>` containing a list of mutable staging row objects and a list of parse warnings.

**Phase 2 — Staging Preview Dialog:** The parsed data is displayed in `_showStagingPreviewDialog()`, which presents the admin with a read-only preview table showing up to 50 rows of parsed data alongside any parse warnings. The dialog contains a "Submit" button that triggers the second phase. At this point, no data has been written to Firestore — the admin can review the data and cancel without side effects.

**Phase 3 — Submission:** When the admin clicks "Submit", the corresponding `submit*` method is called. For students, this creates Firebase Auth accounts for each row (gracefully skipping email-already-in-use errors) and writes student documents to Firestore. For courses, it writes course documents. For grades, it performs additional cross-validation: it confirms that the student ID exists in the `students` collection, that the course code exists in the `courses` collection, and that no duplicate grade record exists for that student/course/semester combination. Each validated grade is written via `Grade.create()`, which automatically computes totalScore and letterGrade from the component scores. The submit result — showing success count and any per-row errors — is displayed in a final summary dialog, and the data tables are reloaded.

### Grade Validation Logic

The admin panel implements three validation checks when manually adding grades, mirroring the logic used during bulk import:

- `_studentExists(studentId)` queries Firestore's `students` collection by `student_id` and returns true if a matching document is found. This prevents grades from being assigned to non-existent student IDs.
- `_courseExists(courseCode)` queries the `courses` collection by `course_code`. This prevents grades from being assigned to non-existent course codes.
- `_hasDuplicateGrade(studentId, courseCode, semester)` queries the `grades` collection for any existing document that matches all three fields and limits to 1 result. If a match is found, the grade is rejected with a clear error message identifying the duplicate.

These three checks are applied both during manual grade entry (in `_showAddGradeDialog()`) and during bulk grade submission (in `ExcelImportService.submitGrades()`), ensuring consistent integrity across both workflows.

## 3.3 The Student Dashboard & History View

### Dashboard Layout

`EnhancedStudentDashboard` serves dual roles: it is both the navigation shell (containing the drawer, top app bar with notification bell and profile avatar, and bottom navigation bar) and the home dashboard content. The dashboard tab (`_buildDashboardTab()`) displays the following sections from top to bottom:

1. **Welcome Banner** — Displays "Welcome back," followed by the student's `fullName` read from `provider.currentStudent`.

2. **Academic Overview Card** — A gradient card showing the current semester name, the number of enrolled courses, and three metric tiles: GPA (for the current semester), CGPA (cumulative across all semesters), and total credits. The GPA and CGPA values are read from `provider.selectedGPA` and `provider.cgpa`, which are computed by `GradeService.calculateGPA()` and `GradeService.calculateCGPA()`. Both methods use the weighted credit-hour formula: for each course, the letter-grade quality point is multiplied by the course's credit hours, the products are summed, and the result is divided by the total credit hours.

3. **Quick Actions** — Three tiles (Grades, GPA, Report) that navigate to tabs 1, 2, or push the `PdfExportScreen`.

4. **Past Results Card** — A white card with a history icon, the title "Past Results", and the subtitle "Check your previous semester grades and CGPA breakdown". Tapping this card calls `_navigateToTab(3)`, which switches the bottom navigation to the History tab and renders the `HistoryScreen`.

5. **Recent Grades** — The four most recent grade records from `provider.grades`, each displayed as a card showing the letter grade badge, course code, course title, and total score.

### Real-Time Data Flow

The dashboard does not perform any manual data fetching. Instead, it relies on three Firestore snapshot listeners initialized in `initializeRealtimeListeners()`: the student data stream listens for changes to the student's Firestore document and updates the `_currentStudent` object if profile fields change; the grades stream listens for new or modified grade documents and reloads the full grade list; the courses stream listens for course catalog changes and rebuilds the course list. Each listener calls `notifyListeners()` after updating its state, which triggers a rebuild of all `Consumer<AppProvider>` widgets in the tree — including the dashboard's gradient card metrics and the recent grades list. This means that if an administrator adds a new grade from the admin panel while the student is viewing their dashboard, the new grade will appear automatically within seconds without the student needing to pull-to-refresh.

### Bottom Navigation Bar

The bottom navigation bar is implemented as a custom floating container (not the standard `BottomNavigationBar` widget) to achieve the rounded pill shape and dark theme. It appears at the very bottom of the screen, wrapped in a `SafeArea` to respect system navigation gestures on edge-to-edge displays. The five navigation items — Home, Grades, GPA, History, and Profile — each have an icon and label. The active tab is highlighted with a semi-transparent primary color overlay. Tapping a navigation item calls `_navigateToTab(index)`, which sets `_currentIndex` and triggers a rebuild, causing `_buildTabContent()` to return the widget for the selected tab.

### History Screen — Semester-by-Semester Breakdown

`HistoryScreen` is a `StatelessWidget` that consumes `AppProvider` to read the student's complete academic data. When the screen loads (either by tapping the bottom nav History item or by tapping the "Past Results" card on the dashboard), it renders:

1. **Summary Stat Cards** — Three horizontal cards showing the total number of semesters (`provider.semesters.length`), the cumulative CGPA (`provider.cgpa`), and the total number of graded courses (`provider.grades.length`). Each card is color-coded using `AppColors.info`, `success`, and `warning` respectively.

2. **Semester History List** — The screen iterates over `provider.semesters` (a sorted list of semester strings extracted from the grade data). For each semester, it calls `provider.getGradesForSemester(semester)` to retrieve the relevant grades and computes a semester-specific GPA using the private `_calcGPA()` helper. This method replicates the weighted credit-hour calculation: it iterates over each grade, looks up the course via `provider.getCourseInfo()`, multiplies `Grade.gradePoint(grade.letterGrade)` by the course's credit hours, sums the weighted points, divides by total credits, and returns the result.

3. **ExpansionTile per Semester** — Each semester is rendered as an `ExpansionTile` with the semester name as the title, the total credit count as the subtitle, and the computed GPA displayed as a colored badge in the trailing position. The badge color is determined by `_gpaColor()`: green for ≥3.7, blue for ≥3.0, amber for ≥2.0, and red for below 2.0. When expanded, the tile shows a summary row (GPA, credits, course count) followed by a `ListTile` for each individual grade, displaying the course code, course title, credit hours, percentage score, and a color-coded letter grade badge.

### Drawer Navigation

The drawer provides an alternative navigation path to all five tabs plus additional options: Notifications (pushes `NotificationScreen`), Export PDF (pushes `PdfExportScreen`), and Logout (calls `provider.logout()` and navigates to `LoginScreen`). The drawer header displays the student's photo (if available), full name, and student ID from the provider.
